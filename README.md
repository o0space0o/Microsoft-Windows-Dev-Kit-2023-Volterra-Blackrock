# Microsoft Volterra

A private ARM64 Microsoft Validation OS live environment for Kevin Thienpont's Windows Dev Kit 2023, with the approved space-themed overlay and a persistent Codex workspace.

The target is a live RAM boot from the existing A: partition. Windows 11 remains the default boot choice. The overlay and project files live in `Volterra` on the prepared persistent drive; private account profiles and conversation history live separately in `VolterraState`. The user does not need to choose a working folder.

There is one current image, under `build/current`, named `Microsoft Volterra.iso`. There are no numbered releases. An image receipt records its exact source commit, WIM and ISO hashes, and verification status. `node scripts/Plan-IsoBoot.mjs` inspects those current files without changing media or a VM. The legacy `Test-IsoBoot.ps1` requires an explicit historical build and cannot operate on the current image. A created ISO is not evidence of a successful boot or working physical hardware.

The earlier live environment booted in an ARM64 Hyper-V VM, opened the overlay and official ChatGPT authorization page, and retained a project witness across distinct boots. Physical Dev Kit boot failed after displaying a cursor and returned to Windows Boot Manager, including after removing the Surface USB hub firmware updater. The replacement uses the retained original LiveOS configuration, its 367 driver packages and native startup supervisor. A separate native launcher starts the overlay as the supervisor's child. The original's earlier diskless VM test did not exercise input or persistent storage: a full test captured the actual startup error, "No marked persistent volume was found." That image lacks Microsoft's Hyper-V guest feature. Its matching feature packages are required for the full VM check. Consult the current image receipt for replacement composition, deployment and test status. The physical restart's cause is not yet established; a VM test or overlay preview does not prove physical boot.

MXC was unavailable; elevated Codex execution failed because Secondary Logon is absent from the supplied Validation OS components. The user approved the compatible unelevated sandbox after its weaker network isolation was explained. First guest sign-in, a saved Codex thread across restart and physical Dev Kit hardware still require their recorded checks.

ChatGPT and GitHub use separate official browser sign-ins. No OpenAI API key is required. A fresh live environment requires its own initial authorization; host credentials are not copied into the ISO. Once authorized, the helper resumes the saved automatic queue, reports live work in its log and chat, reviews and checks source increments, and publishes successful changes to main. Questions appear in the conversation. Say “pause” or “continue” to control work. Security-sensitive permissions still require an explicit answer.

The four approved reference images remain byte-identical in `design/approved-v1`. The baseline displays use the reference rasters with interactive hit areas. The live log and chat are a working prototype; they are not a complete reconstruction of every custom control. Compare rendered screens at 1672 × 941 before claiming a visual match.

For the Windows development preview, run `npm start` and open `http://127.0.0.1:43123/?screen=connections`. Ctrl+` opens the live workspace. Read-only system queries include “show devices”, “show services”, “show service dependencies”, “show drives”, “show storage”, “show files”, “show networking”, “show DNS”, “show logs”, “show processes”, “show memory”, “show uptime”, “show processors”, “show maintenance” and “check artwork”. Measurements report unavailable APIs and errors rather than implying hardware acceptance.

Run `node scripts/Check-Source.mjs` to check source boundaries, credential exclusions, locked artwork, syntax and the independent test suite. `scripts/Prepare-ImageSource.mjs` exports and verifies an immutable snapshot of clean, published main. `scripts/Build-LiveIso.ps1` refreshes a hash-pinned, already composed private ARM64 Validation OS boot WIM, verifies the source-bound native helper, seals a credential-free persistent seed and builds the UEFI live ISO. It requires administrator rights, the private runtime, Microsoft image tooling, the sealed base WIM/media and their hashes, and the private sandbox approval record. It refuses to overwrite an existing current image. The approved sandbox mode is sealed into the boot payload and restricted to live Validation OS. An actual sandbox command must pass before agent work starts. Earlier numbered-build tooling is historical and does not select this live image.

For the original native-supervisor base, compile `scripts/Launch-Volterra.cpp` with `scripts/Build-VolterraLauncher.ps1` and supply its private build receipt through `-LauncherReceipt`. The build verifies the retained compiler archive and extracted toolchain. Image staging binds the launcher's source and build-script hashes to the selected source snapshot, verifies the ARM64 executable, preserves the admitted Windows configuration and supervisor, and records separate launcher provenance. Unsupported or mismatched startup configurations stop the build. The launcher captures early child output in `X:\Windows\Temp\VolterraLauncher` and displays a bounded error message before returning to the supervisor. It never restarts the OS on a helper failure. A compiled launcher still requires a guest boot test.

`scripts/Deploy-LiveBoot.ps1` prepares an empty, explicitly identified A: data partition from the VM-verified current image. It verifies copied files, backs up the host BCD, creates its own ramdisk options and Microsoft Volterra loader, and retains the existing Windows default. It neither formats a disk nor restarts the host. A physical boot is a separate check.

Helper updates are reviewed and tested in a detached snapshot, pinned by commit and file hashes, and staged for startup. The sealed bootstrap retains prior source and restores an unconfirmed update. Changes to Windows, drivers or firmware need a separately verified offline boot image and recovery path. The helper reports restart requirements; it never restarts the host automatically.
