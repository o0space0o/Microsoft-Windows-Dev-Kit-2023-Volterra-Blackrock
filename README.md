# Microsoft Volterra

A private ARM64 Validation OS development image and a space-themed local helper for the Windows Dev Kit 2023. The project belongs to Kevin Thienpont.

The helper configures its workspace automatically. On the installed development OS, the workspace is the OS root. On ordinary Windows, the preview uses this build project. Browser sign-in uses the ChatGPT plan or Codex-managed ChatGPT authentication; GitHub has a separate browser sign-in. No OpenAI API key is required. Account profiles and credentials are excluded from image staging.

Run the preview with `npm start`, then open `http://127.0.0.1:43123/?screen=connections`. Press Ctrl+` to show the live workspace. It supports messages, streamed command output, project history, pause, interrupt, resume, file editing and Codex review. The approved artwork remains byte-identical. Exact pixel comparison passes for all four baseline screens at 1672 × 941; the working panel is a new prototype state and needs separate visual approval.

Say “show services” or “show services matching <text>” in the existing chat to read the local Windows Service Control Manager. The helper reports actual service names, state and startup mode, records the observation in its persistent conversation and labels the OS edition/build that supplied it. Filtering is literal and never enters a PowerShell command. This read-only tool works independently of ChatGPT sign-in and does not start, stop or reconfigure services. PowerShell and policy permission to execute the original collector script are prerequisites; missing APIs or denied script execution are reported as blocked, without changing policy. Host readings do not establish Validation OS or hardware acceptance; target availability still needs a real Validation OS test.

Say “show devices” or “show devices matching <text>” to read the local [Win32_PnPEntity inventory](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-pnpentity). Literal filtering matches device names, classes and instance IDs after collection. The saved chat output reports status, presence and numeric problem codes; absent properties remain unreported. Inventory does not prove NPU, driver or physical hardware functionality. The fixed collector requires Windows PowerShell, its local CIM provider and policy permission to run; it never enables/disables devices or installs drivers. Devices and services share the live checking state and run without ChatGPT sign-in.

Say “show storage” to read total, used, free and available capacity for the filesystem containing the selected workspace. The original Node collector uses the [filesystem capacity API](https://nodejs.org/api/fs.html#fspromisesstatfspath-options), preserves integer precision, checks the workspace identity during collection and saves the timestamped report in chat without requiring account sign-in. It reads filesystem capacity only; physical disk identity, other volumes, partition layout and recovery acceptance remain pending. Unavailable APIs or inconsistent readings are reported as blocked. No storage settings are changed.

Say “show networking” or “show networking matching <text>” to read assigned IPv4/IPv6 addresses from the local [Node interface address API](https://nodejs.org/api/os.html#osnetworkinterfaces). “Show network” also works. The saved report includes interface names, netmasks, internal flags and IPv6 scope IDs; filtering matches names or addresses literally after collection. This inventory covers interfaces with assigned addresses and does not establish link state, gateway/DNS settings, connectivity or target hardware acceptance. Collection generates no network traffic or settings changes and runs without account sign-in. Unavailable APIs and malformed readings are reported as blocked.

Say “show files” or “show files matching <text>” to inventory the selected workspace root through the [Node directory API](https://nodejs.org/api/fs.html#fspromisesopendirpath-options) and [entry metadata API](https://nodejs.org/api/fs.html#fspromiseslstatpath-options). The saved chat report shows names, entry types, exact file sizes and modification times. Literal filters apply after collection; supplied path fields do not change the scope. The read-only collector never reads file contents, descends into folders or follows entry links. It skips private build/runtime folders, credential/media names and both configured and canonical paths of its own state directory before reading entry metadata. Missing APIs, denied access, excessive entries, a changed workspace directory or a changed state mapping are reported as blocked. This is a metadata inventory, not an atomic filesystem snapshot, content editor or target OS acceptance test.

Say “show logs” or “show logs matching <text>” to read the newest 50 metadata records from each local System and Application channel with [Get-WinEvent](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.diagnostics/get-winevent?view=powershell-5.1). The saved chat report includes provider, time, event ID, exact record ID and numeric level. Filtering is literal and applies only to this bounded sample, after collection. Event messages, XML, identity fields and Security logs are excluded. Channel errors remain blocked even when another channel returns useful partial readings; missing APIs or script-execution permission produce a saved blocked report. No log is cleared or configured. These readings do not establish a complete event history, system health or Validation OS acceptance.

Say “show maintenance” or “show restart requirements” to read the local [Windows Update restart property](https://learn.microsoft.com/en-us/windows/win32/api/wuapi/nf-wuapi-isysteminformation-get_rebootrequired) and whether [pending file operations](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw) contain queued filename entries. The saved chat shows each provider separately and keeps missing APIs or denied reads blocked. A positive reading survives a failure of the other provider; when no positive reading exists and a provider failed, requirements remain unknown. Queued paths, update contents and credentials are excluded. The read-only collector does not install updates, change registry values or restart the system. This limited query cannot rule out restart requirements from other installers, component servicing, firmware or staged helper updates and does not verify recovery or target OS acceptance. Broader maintenance actions remain under development.

Say “show processes” or “show processes matching <text>” to inventory local process IDs, names, session IDs and exact [working-set bytes](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.workingset64?view=netframework-4.8.1) with [Get-Process](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/get-process?view=powershell-5.1). Literal filtering by name or PID happens after collection. Unavailable optional properties remain unreported rather than becoming zero; denied enumeration or script execution is saved as blocked. The query reads no command lines, executable paths or owners and never stops processes or changes their priority. Processes can exit or change during collection and PIDs can be reused; this is not an atomic snapshot, a performance test or system-health/Validation OS acceptance evidence. Policy-authorized execution of the fixed collector and a real target test remain prerequisites.

The configured repository is [o0space0o/Microsoft-Windows-Dev-Kit-2023-Volterra-Blackrock](https://github.com/o0space0o/Microsoft-Windows-Dev-Kit-2023-Volterra-Blackrock), branch main. Startup on Validation OS resumes the saved automatic queue and Codex thread after browser authorization. Pause persists across restarts. Each source increment receives Codex review and independent source/tests checks before a main commit and non-force push. Conflicts, failed checks and missing credentials retain the work and show the blocker. The GitHub connection inside Codex desktop is separate from the helper's GitHub CLI authorization.

Remote main changes are reviewed and tested in a detached snapshot, pinned by commit and file hashes, and staged for startup. A sealed bootstrap preserves changed files and restores them on the next launch if runtime health was not confirmed. This implements helper source updates and rollback. Windows, driver and firmware image updates still require a verified boot/recovery workflow. The helper reports restart requirements and does not restart the machine automatically.

`node scripts/Check-Source.mjs` checks source boundaries, credential exclusions, locked artwork, JavaScript syntax and the test suite. Tests cover queue persistence, review/check gates, conflict handling, startup rollback, tamper detection, local endpoint authorization, agent interruption/resumption and automatic system workspace selection. `node test/live-codex.mjs` checks actual ChatGPT-backed Codex inference and structured queue outcomes. The visual test uses Playwright and pngjs from the configured bundled runtime.

Image composition uses an isolated ARM64 Windows PE technician VM because this host rejects offline Validation OS registry hives. The technician attaches only its own virtual disks, has no network adapter, and stages the original Microsoft image, runtime packages, verified device-driver catalogs and credential-free helper payload. Firmware update packages are excluded. Servicing receipts are distinct from OS boot, runtime and physical-device acceptance.

`node scripts/Prepare-ImageSource.mjs` prepares a private source snapshot without elevation or image servicing. It requires clean, published main, exports only approved files from that exact Git commit, runs independent source checks and records every file hash. Verification compares the complete manifest with Git objects and published ancestry and reruns the checks. The finalizer consumes this snapshot instead of the live agent's working folder, removes individually identified obsolete source files, rejects destination junctions, verifies source/bootstrap/startup copies and records the same source commit in the image and ISO receipts. Private runtime and vendor OS files remain outside the source reconciliation. ISO creation checks the copied WIM hashes. `Refresh-HelperImage.ps1 -SourceReceipt <receipt path>` consumes a prepared snapshot when image servicing is permitted. Preparing a snapshot does not build, boot or install an OS. Existing media without this source binding remains an earlier development artifact.

`Test-IsoBoot.ps1 -BuildName development-007` selects that build's ISO receipt, VM identity and private virtual disk paths; the default remains `development-006` with its original name and ISO filename. The read-only `Plan-IsoBoot.mjs` helper checks the selected ISO hash/size, receipt hash and matching image/finalization source commit before Hyper-V is used. New VM identities pin these bindings. Existing unbound 006 identities remain usable for Inspect/Stop and are reported as `legacy-unbound`, with no inferred source commit. The test retains generation 2 and Microsoft Windows Secure Boot, rejects unexpected disk/network attachments and does not attach physical disks. A successful phase is not OS boot or runtime acceptance. Source fixture tests do not run Hyper-V or refresh media; those operations and physical/recovery acceptance remain pending.

The existing Windows 11 default boot entry is preserved. The A: candidate description has been renamed to Microsoft Volterra and a boot configuration backup is saved under build/boot-rename. Installation and runtime acceptance remain pending until the composed image passes its VM boot checks.

`scripts/Test-BootRuntime.ps1` writes version 2 runtime evidence with separate checks and missing prerequisites. On ordinary Windows it writes only `build/verification/boot-runtime-host.json` and stops before guest probes or update confirmation. On a booted Validation OS it checks the automatic OS root, staged executables, native sandbox readiness and read-only execution, this OS’s Codex-managed ChatGPT sign-in, and a separate staged-browser script/render smoke test. The capture is not a pixel-match or fresh browser authorization test. Missing account, browser or sandbox evidence is blocked; initialization alone cannot pass. Dynamic app-managed sign-in still requires separate runtime verification.

Persistent history acceptance requires a readable saved thread and journal outside public source, with Codex history under the persistent state directory. A private witness retains the same thread across distinct OS boot times; repeated probes in one session do not prove reboot persistence. Run the verifier again after sign-in and after a user-controlled reboot to collect missing evidence. Source startup health is reported separately so missing first sign-in or reboot evidence does not roll back healthy helper source. These reports do not establish VM boot, physical device, recovery or image-refresh acceptance. No reboot is initiated.

The verifier waits for the helper’s explicit runtime readiness, then refreshes its authenticated snapshot after the browser and standalone Codex checks. A stopped helper cannot reuse its earlier healthy snapshot, and persistent history evidence must name the thread selected in the refreshed snapshot. Canonical Codex directories must stay on the persistent storage volume, inside its private state folder and outside public source; directory junctions cannot bypass these checks. Polling does not initiate sign-in or grant permissions.
